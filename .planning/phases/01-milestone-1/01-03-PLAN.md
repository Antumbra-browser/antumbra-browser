  Step 2: Create prefs/policies.json with the following content.

  NOTE (check 1 resolution): `${DISTRIBUTION_CUSTOMIZATION_SEARCH_PATH}` is NOT a
  supported variable in ExtensionSettings install_url. It appears only in the Firefox
  Search Service subsystem and is not expanded by the policies engine (Policies.sys.mjs).
  The policies engine only expands `${home}`, and only for download directory settings,
  never for install_url. Using it in install_url causes Firefox to try fetching a URL
  with that literal string, which fails silently.

  The correct bundling mechanism for local XPIs is `distribution/extensions/<addon-id>.xpi`.
  Firefox auto-installs any XPI placed in that directory on first startup. This is the
  standard approach used by Mozilla's own enterprise deployment documentation. The
  install_url field in policies.json is NOT needed when using this mechanism.

  The policies.json entries below set installation_mode and updates_disabled only.
  The actual installation is triggered by the XPI files in distribution/extensions/,
  which package-extensions.sh (Task 2, Step 4) populates during the build packaging step.

  ```json
  {
    "policies": {
      "ExtensionSettings": {
        "uBlock0@raymondhill.net": {
          "installation_mode": "normal_installed"
        },
        "Consent-O-Matic@cavi.au.dk": {
          "installation_mode": "normal_installed"
        },
        "@testpilot-containers": {
          "installation_mode": "normal_installed"
        }
      },
      "DisableSystemAddonUpdate": true,
      "DisableTelemetry": true,
      "DisableFirefoxStudies": true,
      "OverrideFirstRunPage": "",
      "DisableFeedbackCommands": true,
      "DisableSetDesktopBackground": false,
      "DontCheckDefaultBrowser": true
    }
  }
  ```

  NOTE (D10): updates_disabled is intentionally absent. Bundled extensions auto-update
  from AMO. uBlock Origin and Consent-O-Matic depend on frequent upstream updates for
  accurate filter lists and consent rule coverage. A stale blocker is a broken blocker.
  The XPIs in distribution/extensions/ are the initial install baseline only, not a
  version pin. See D10 in DECISIONS.md and docs/extension-update-process.md.

  Step 4: Create a scripts/package-extensions.sh script that copies
  third_party/extensions/*.xpi into the build output's distribution/extensions/ directory,
  renamed to <addon-id>.xpi so Firefox auto-installs them on first startup.
  This is the `distribution/extensions/` mechanism -- no install_url needed in policies.json.

  Extension ID to directory mapping (canonical AMO IDs):
  - ublock-origin      -> uBlock0@raymondhill.net
  - consent-o-matic    -> Consent-O-Matic@cavi.au.dk
  - multi-account-containers -> @testpilot-containers

  ```sh
  #!/usr/bin/env bash
  # Copy vendored extension .xpis to the build output's distribution/extensions/ directory.
  # Firefox auto-installs any <addon-id>.xpi found there on first startup.
  # Called by scripts/package.sh after ./mach package.
  set -euo pipefail

  REPO_ROOT="$(cd "$(dirname "$0")/.." && pwd)"
  OBJDIR="${1:-obj-x86_64-pc-mingw32}"
  DIST_DIR="D:/dev/antumbra/firefox/${OBJDIR}/dist/bin/distribution/extensions"

  declare -A EXT_IDS=(
    [ublock-origin]="uBlock0@raymondhill.net"
    [consent-o-matic]="Consent-O-Matic@cavi.au.dk"
    [multi-account-containers]="@testpilot-containers"
  )

  mkdir -p "${DIST_DIR}"
  for ext_dir in "${REPO_ROOT}/third_party/extensions"/*/; do
    ext_name="$(basename "${ext_dir}")"
    ext_id="${EXT_IDS[$ext_name]:-}"
    if [[ -z "${ext_id}" ]]; then
      echo "WARNING: no extension ID mapping for ${ext_name}; skipping."
      continue
    fi
    for xpi in "${ext_dir}"*.xpi; do
      if [ -f "${xpi}" ]; then
        cp "${xpi}" "${DIST_DIR}/${ext_id}.xpi"
        echo "  Copied ${ext_name} -> ${ext_id}.xpi"
      fi
    done
  done
  echo "Extensions copied to ${DIST_DIR}"
  ```

  Context on auto-updates (D10):
  - Bundled extensions auto-update from AMO. The XPI in distribution/extensions/ installs
    the baseline version on first startup. After that, Firefox's addon update service

  - The vendored XPI is a shipping baseline, not a frozen pin. Users who install

  - This process exists to keep the shipped baseline current so new installs start
    at a recent version, not one that is months out of date.

  ```markdown

  Once installed, extensions auto-update from AMO (D10 in DECISIONS.md). This process
  updates the vendored XPI so that new Antumbra installs start at a recent version.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| AMO download → third_party/extensions/ | Extension .xpi files are downloaded from Mozilla's CDN; any tampering between download and vendor would ship a malicious extension to every user. |
| policies.json → extension installation | policies.json with installation_mode: normal_installed causes Firefox to install extensions silently on launch; a wrong extension ID or install_url could install a different extension. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-03-01 | Tampering | third_party/extensions/ .xpi files | mitigate | Record SHA-256 of each downloaded .xpi in THIRD-PARTY.md. The license-check CI job (plan 01-06) verifies that every third_party/ entry has a LICENSE file and a THIRD-PARTY.md row. Version bumps require a deliberate diff review. |
| T-01-03-02 | Spoofing | policies.json extension IDs | mitigate | Extension IDs are hardcoded and match the AMO canonical IDs. A wrong ID would silently fail to install; verified by checking about:policies after build. |
| T-01-03-03 | Tampering | policies.json "installation_mode" | mitigate | Using "normal_installed" (not "force_installed") means the user CAN remove extensions (ARCHITECTURE.md 6.2 requirement). "force_installed" would be a regression; grep-verifiable. |
| T-01-03-04 | Information Disclosure | uBlock Origin filter list updates | accept | uBlock Origin fetches filter list updates from its own servers (Tuxfamily CDN). This is expected behavior; it is not telemetry and does not send user data. Disclosed in onboarding (plan 01-05). |

Note: No user data is handled in Milestone 1 repo files. Extension signing enforcement stays on (D3); the bundled extensions are Mozilla-signed AMO builds.
</threat_model>
